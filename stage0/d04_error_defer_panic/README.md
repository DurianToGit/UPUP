4. Sentinel Error 有什么优缺点。
回答：Sentinel Error（哨兵错误） 是 Go 语言中一种基础且常见的错误处理模式，指在包级别预定义并导出的特定错误变量，用于在程序中标识特定的错误条件。它并非完美的万能方案，而是一种在特定场景下有效的工具

优点： 简单、清晰、高效
   - 语义明确，简单直接：Sentinel Error 最大的优点是清晰易懂。
   - 使用和检查高效：其检查方式非常直接。在没有对错误进行包装（wrapping）时，可以直接使用 == 运算符与预定义的错误变量进行比较。即使错误被包装，也可以通过 errors.Is 函数在错误链中高效地检查
   - 提供一致的错误“语言”：在整个代码库或项目中，使用统一的 Sentinel Error 集合，可以保证对相同错误情况（如“记录不存在”）的处理方式保持一致，提高了代码的可维护性

缺点：耦合、脆弱与僵化
  - 创建包之间的源码依赖：这是 Sentinel Error 最严重的问题
  - 增加 API 的暴露面（表面积）：导出的 Sentinel Error 变量成为了你公共 API 的一部分
  - 灵活性差，脆弱易碎
    - 难以添加上下文
    - 可能被意外修改
  - 阻碍系统演进：由于上述的依赖和 API 暴露问题，一旦广泛使用了 Sentinel Error，对其进行任何修改都会变得异常困难，因为它们可能被大量外部代码所依赖。这会导致项目的演进被“锁死”

errors.As：
1. errors.Is 和 errors.As 的区别；
回答：errors.Is比较的时值，errors.As是类型匹配
2. 为什么 errors.As 的第二个参数通常需要传指针
回答：这涉及 Go 的类型系统和反射赋值机制，
   - 需要修改外部变量的值：errors.As 的作用是“将错误链中匹配的错误赋值给目标变量”。如果不传指针，传的是目标变量的拷贝，函数内部修改拷贝无法影响外部的原始变量。 
   - 接口变量的特殊性：第二个参数的类型是 any（空接口）。如果写成 var e MyError 并传入 e（值类型），As 内部拿到的是 MyError 的副本，且无法将其动态赋值为其他具体类型（因为MyError 的静态类型已定）。传入 *MyError 指针，As 内部才能通过反射调用 reflect.ValueOf(dst).Elem() 来设置指向具体错误对象的指针。 
   - 实现细节约束：errors.As 源码内部要求传入的参数是非空指针（dst 是指针且不能为 nil），否则会直接 panic。这是为了确保提取出的错误能被安全地回填到调用方的变量中。

3. 自定义 Error 相比字符串 Error 有什么价值。
回答：自定义 Error 的价值在于将错误从“文本描述”升维为“数据结构”，让程序不仅能判断“发生了什么”，还能知道“发生了什么细节”并据此做出智能决策，而不必脆弱地解析字符串。这也是 Go 官方推荐在公共 API 中优先使用自定义错误类型的原因

4. 生产代码是否应该大量依赖这种技巧。

回答： 不建议大量依赖，原因如下：

   - 可读性差：defer 中修改命名返回值会隐式改变函数结果，阅读代码时容易忽略，增加理解成本。

   - 维护困难：后续修改可能引入意外副作用，尤其当 defer 逻辑复杂或嵌套多层时。

   - 调试复杂：执行顺序（赋值 → defer → 返回）不够直观，容易导致预期外的行为。
     
适用场景（可谨慎使用）：
- 统一修改错误返回值（如将 error 包装成自定义错误）。

- 资源释放时需要对返回结果进行修正（如关闭文件后更新状态）。

- 需要在返回前执行某些清理逻辑，并确保清理后返回正确的值。
